ב-AWS יש הרבה יותר ממאה שירותים, והתפריט בקונסולה נראה כמו חומה. החדשות הטובות הן שליבה קטנה עושה את רוב העבודה: מקום לשמור קבצים, מקום להריץ קוד, רשת מסביב, מסד נתונים, ודרך לשלוט במי מורשה לגעת במה. כשמכירים את אלה, השאר הוא וריאציות.

המדריך הזה הוא מפה, לא ספר הוראות. הוא עובר על שירותי הליבה לפי הסדר שבו פוגשים אותם, מראה את הטעויות שמתחילים עושים (בעיקר באבטחה ובעלויות), ומפנה לתיעוד הרשמי לפרטים. מחירים, תוכניות חינמיות ותפריטי קונסולה משתנים לעתים קרובות, אז אני מתאר רעיונות ומפנה למקור במקום לצטט מספרים.

## מה זה AWS

AWS היא פלטפורמת ענן: במקום לקנות שרתים, שוכרים כוח חישוב, אחסון ורשת דרך האינטרנט ומשלמים על מה שמשתמשים בו. יוצרים משאבים בכמה לחיצות או בפקודה אחת, ומוחקים אותם כשמסיימים.

שני רעיונות כדאי שיהיו ברורים לפני הכול:

- **כל דבר הוא שירות עם API.** הקונסולה, שורת הפקודה והקוד שלנו קוראים לאותם APIs. כל מה שאפשר ללחוץ עליו אפשר גם לסקריפט.
- **אחריות משותפת.** AWS מאבטחת את הענן עצמו: מרכזי נתונים, חומרה, שכבת הוירטואליזציה. אנחנו מאבטחים את מה שהכנסנו אליו: מי מקבל גישה, איך הדברים מוגדרים, הנתונים שלנו, ומערכת ההפעלה של כל שרת שאנחנו מריצים בעצמנו. bucket ציבורי ב-S3 שמדליף מידע הוא בעיה של הלקוח, לא של AWS. ככל שהשירות מנוהל יותר (שירות מסד נתונים במקום שרת שאנחנו מתחזקים), AWS לוקחת עליה יותר.

## המפה: Regions ואזורי זמינות

משאבי AWS חיים במקומות פיזיים. שלוש מילים מכסות את זה:

- **Region** הוא אזור גאוגרפי עם מרכזי נתונים משלו, בשמות כמו `eu-central-1` (פרנקפורט) או `us-east-1` (וירג׳יניה). ה-Regions מבודדים זה מזה, והנתונים שלנו נשארים ב-Region שבחרנו אלא אם מעבירים אותם.
- **אזור זמינות (Availability Zone, או AZ)** הוא מרכז נתונים אחד או יותר בתוך Region, עם חשמל, קירור ורשת נפרדים. האזורים ב-Region מחוברים בקווים מהירים, ומתוכננים כך שתקלה באחד לא מפילה את האחרים.
- **Edge location** היא נקודת נוכחות שבה שירותים כמו CloudFront (CDN) מגישים תוכן קרוב למשתמשים.

![Region מכיל שלושה אזורי זמינות, כל אחד מורכב ממרכזי נתונים עם חשמל, קירור ורשת משלהם, ומחוברים בקווים עם השהיה נמוכה. Region שני עומד בנפרד ומבודד מהראשון.](/images/aws-zero-to-hero/regions-and-azs.svg)

שתי תוצאות מרגישים מיד. הראשונה: **כמעט הכול הוא לפי Region**. בסרגל העליון בקונסולה יש בורר Region, ו-bucket או שרת שיצרנו "נעלמים" אם מסתכלים על ה-Region הלא נכון. השנייה: **זמינות גבוהה אומרת להשתמש ביותר מ-AZ אחד**, כי AZ בודד יכול ליפול. בוחרים Region לפי המרחק מהמשתמשים (השהיה), המחיר, אילו שירותים קיימים בו, וכללים חוקיים על המקום שבו מותר לשמור נתונים.

אפשר לרשום את האזורים של Region מה-CLI (נתקין אותו עוד מעט):

```bash
aws ec2 describe-availability-zones --region eu-central-1 \
  --query "AvailabilityZones[].{Zone:ZoneName,State:State}" --output table
```

## החשבון שלנו, בצורה בטוחה

נרשמים ב-[aws.amazon.com](https://aws.amazon.com/). יוצרים חשבון עם אימייל, סיסמה ואמצעי תשלום. הזהות הראשונה הזו היא **משתמש ה-root**, והוא יכול לעשות הכול, כולל לסגור את החשבון. מתייחסים אליו כמו אל מפתח האב:

1. **מפעילים MFA למשתמש ה-root מיד**, רצוי עם passkey או מפתח אבטחה. זה הדבר היחיד הכי מועיל שאפשר לעשות.
2. **לא עובדים עם root ביום-יום.** יוצרים לעצמנו זהות רגילה (בפרק הבא) ומשאירים את ה-root לכמה משימות שדורשות אותו.
3. **אף פעם לא יוצרים access keys ל-root.**

### תוכנית חינמית, קרדיטים וחשבוניות

ההצעה החינמית של AWS השתנתה עם הזמן, אז בודקים בדף [AWS Free Tier](https://aws.amazon.com/free/) ולא בפוסט ישן (כולל הפוסט הזה). נכון לזמן הכתיבה, חשבון חדש יכול להתחיל ב-**Free plan**: מגיעים איתו קרדיטים, והחשבון נסגר אחרי תקופה מוגדרת או כשהקרדיטים נגמרים, אלא אם עוברים ל-**Paid plan**. ב-Paid plan יש גישה לכל השירותים והחיוב הוא לפי שימוש. כמה שירותים הם "תמיד חינם" בתוך מכסות חודשיות. בכל תוכנית העיקרון זהה: **המכסה החינמית היא גבול, לא הבטחה שדבר לא יכול לעלות כסף.**

לפני שיוצרים משהו, מגדירים תקציב:

- פותחים **Billing and Cost Management ← Budgets** ויוצרים **cost budget** עם סכום חודשי קטן, למשל 10 דולר, עם התראות באימייל באחוז ממנו ולפי תחזית.
- חשוב לדעת שנתוני התקציב מתעכבים: לפי AWS הם מתעדכנים עד שלוש פעמים ביום, והתיעוד מזהיר שחיובים יכולים לעבור את הסף לפני שההתראה מגיעה. תקציב הוא גלאי עשן, לא תקרת הוצאה.

כדאי גם להציץ מדי פעם ב-**Billing ← Bills** וב-**Cost Explorer**. רוב החשבוניות המפתיעות נובעות ממשהו ששכחנו לכבות (את החשודים הרגילים נרשום בסוף).

## IAM: מי יכול לעשות מה

**IAM (Identity and Access Management)** הוא השירות שמחליט מי מורשה לעשות מה, והוא חינמי. החלקים:

- **Principal** הוא מי שמבצע בקשה: אדם, אפליקציה או שירות של AWS.
- **User** הוא זהות ארוכת טווח עם סיסמה ו/או access keys. **Group** היא קבוצת משתמשים שחולקים הרשאות.
- **Role** היא זהות עם הרשאות ש*כל אדם או דבר יכול לקחת על עצמו לזמן קצר*, ולקבל בעזרתה credentials קצרי טווח. מופעי EC2 ופונקציות Lambda משתמשים ב-roles, כך שהקוד שלנו לא צריך סיסמה שמורה.
- **Policy** היא מסמך JSON שאומר מה מותר ומה אסור.

כך נראית policy: היא מתירה לקרוא אובייקטים מ-bucket אחד, ושום דבר אחר.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::my-example-bucket/*"
    }
  ]
}
```

כללי ההערכה קצרים: **הכול אסור כברירת מחדל**, `Allow` פותח משהו, ו-`Deny` מפורש תמיד גובר על כל `Allow`.

![Principal שולח בקשה. בדיקת ה-IAM policy מחפשת Allow מתאים, ו-Deny מפורש תמיד גובר. אם מותר, הבקשה מגיעה למשאב, למשל bucket ב-S3. בלי Allow מתאים הבקשה נדחית עם AccessDenied.](/images/aws-zero-to-hero/iam-permissions.svg)

השיטות המומלצות הרשמיות מסתכמות בכמה הרגלים:

- **מעדיפים credentials זמניים על פני ארוכי טווח.** לבני אדם AWS ממליצה על federation, ו-**IAM Identity Center** הוא האפשרות המרכזית לניהול גישה לחשבונות שלנו. לאפליקציות משתמשים ב-**roles**.
- **דורשים MFA** בכל מקום שיש בו משתמשים.
- **מיישמים least privilege.** אפשר להתחיל מ-policies מנוהלות של AWS אם זה נוח, ואז לצמצם. כלים כמו IAM Access Analyzer יכולים לייצר policy הדוקה יותר לפי הפעילות שראו.
- **סוקרים ומסירים** משתמשים, roles ומפתחות שלא בשימוש, באופן קבוע.

בחשבון אישי המתכון המעשי הוא: מפעילים את IAM Identity Center, יוצרים לעצמנו משתמש עם permission set שהוא *לא* מנהל מלא אלא אם צריך, ונכנסים דרך הפורטל שלו. נמנעים מיצירת משתמשי IAM עם access keys ומהדבקת המפתחות האלה בקבצים וב-repos: מפתחות שדלפו הם הדרך שבה חשבונות נחטפים כדי לכרות קריפטו על חשבוננו.

## ה-AWS CLI

את כל מה שלמעלה אפשר לעשות בקונסולה, אבל ה-**AWS CLI** הוא הדרך לסקריפט ולחזור על פעולות. מתקינים את גרסה 2 לפי [המדריך הרשמי](https://docs.aws.amazon.com/cli/latest/userguide/getting-started-install.html), ואז נכנסים עם credentials קצרי טווח:

```bash
aws --version
aws login                    # sign in with your console credentials (short-term credentials)
# or, with IAM Identity Center:
aws configure sso            # a wizard: SSO start URL, region, account, role, profile name
aws sts get-caller-identity  # who am I, and which account?
```

`aws sts get-caller-identity` היא הפקודה הראשונה שמריצים בכל טרמינל חדש: היא עונה על "באיזה חשבון ואיזו זהות אני משתמש עכשיו?", השאלה שעומדת מאחורי הרבה טעויות יקרות. ה-CLI שומר את ההגדרות ב-profiles, ב-`~/.aws/config` וב-`~/.aws/credentials`. בוחרים אחד לכל קריאה עם `--profile`, או לכל טרמינל עם משתנה סביבה:

```bash
aws s3 ls --profile dev
export AWS_PROFILE=dev
aws configure list           # shows which profile, region and credentials are in effect
```

התיעוד מונה access keys ארוכי טווח (`aws configure` עם מפתח וסוד) כאפשרות שהוא לא ממליץ עליה. משתמשים בהם רק אם משהו באמת לא יכול להשתמש בשום דבר אחר, ואף פעם לא עושים להם commit.

## S3: קבצים בענן

**Amazon S3 (Simple Storage Service)** שומר אובייקטים: קובץ יחד עם metadata. זה השירות הנפוץ ביותר ב-AWS, והדבק של הרבה שירותים אחרים (גיבויים, נכסים של אתרים, data lakes, לוגים).

- **Bucket** הוא מכל לאובייקטים. השם שלו חייב להיות ייחודי גלובלית (בכל חשבונות AWS), ובוחרים Region כשיוצרים אותו. אי אפשר לשנות לאחר מכן את שם ה-bucket או להעביר אותו ל-Region אחר.
- ל**אובייקט** יש **key**, שמו הייחודי בתוך ה-bucket. אין תיקיות אמיתיות: `photos/2026/cat.jpg` הוא פשוט key ארוך, והקונסולה מציגה את הלוכסנים כתיקיות מטעמי נוחות (זה "prefix").
- אובייקטים יכולים להיות גדולים כמה שצריך, ו-S3 גובה על מה ששומרים, על בקשות ועל נתונים שיוצאים החוצה.

כמה דברים שכדאי לדעת מההתחלה:

- **Buckets פרטיים כברירת מחדל**, ו-**Block Public Access** פועל כברירת מחדל. משאירים את זה כך אלא אם באמת צריך קבצים ציבוריים. רוב הדליפות מ-S3 הן bucket שמישהו הפך לציבורי בטעות.
- **Versioning** שומר כל גרסה של אובייקט, כך שאפשר לבטל דריסה או מחיקה בטעות.
- **Storage classes** מחליפים מחיר במהירות גישה: S3 Standard לגישה תכופה, classes זולים יותר לגישה נדירה (Infrequent Access), ו-classes של Glacier לארכיון. **Lifecycle rules** מעבירים או מוחקים אובייקטים אוטומטית ככל שהם מתיישנים.
- S3 מספק **strong read-after-write consistency**: אחרי העלאה מוצלחת, הקריאה או הרשימה הבאה כבר רואות אותה.

פקודות ה-CLI ברמה הגבוהה (`aws s3`) מרגישות כמו מנהל קבצים:

```bash
aws s3 mb s3://my-unique-bucket-name          # create a bucket (make-bucket)
aws s3 ls                                     # list your buckets
aws s3 cp notes.txt s3://my-unique-bucket-name/   # upload
aws s3 ls s3://my-unique-bucket-name/         # list the contents
aws s3 cp s3://my-unique-bucket-name/notes.txt ./ # download
aws s3 sync ./site s3://my-unique-bucket-name/site # upload only what changed
aws s3 presign s3://my-unique-bucket-name/notes.txt --expires-in 3600   # temporary download link
```

**Presigned URL** נותן למישהו גישה מוגבלת בזמן לאובייקט פרטי אחד בלי להפוך את ה-bucket לציבורי, וזו בדרך כלל התשובה הנכונה ל"איך משתפים את הקובץ הזה?".

לשתי פקודות מגיעה אזהרה. `aws s3 sync ... --delete` מוחקת גם אובייקטים ביעד שאינם במקור, ו-`aws s3 rm ... --recursive` מוחקת הכול מתחת ל-prefix. מוסיפים קודם `--dryrun` כדי לראות מה יקרה. כשמסיימים להתנסות, מרוקנים את ה-bucket ומסירים אותו: `aws s3 rb s3://my-unique-bucket-name --force`.

## EC2: שרתים וירטואליים

**Amazon EC2 (Elastic Compute Cloud)** משכירה שרתים וירטואליים, שנקראים **instances**. זה הדבר הקרוב ביותר ל"מחשב בענן" והשירות הגמיש ביותר, מה שאומר גם שאנחנו אחראים למה שרץ עליו. אוצר המילים:

- **AMI (Amazon Machine Image)** היא התבנית של ה-instance: מערכת ההפעלה וכל תוכנה שהותקנה מראש. בוחרים אחת בהפעלה (Amazon Linux, Ubuntu, Windows...).
- **Instance type** הוא גודל החומרה: משפחה וגודל, כמו `t3.micro`. כל type הוא איזון אחר בין CPU, זיכרון, רשת ואחסון.
- **Key pair** היא הדרך להיכנס דרך SSH: AWS שומרת את המפתח הציבורי, ואנחנו שומרים את הפרטי. מי שמאבד את המפתח הפרטי לא יכול להיכנס בדרך הזו.
- **Security group** היא חומת אש וירטואלית סביב ה-instance: היא מפרטת אילו פרוטוקולים, פורטים וטווחי כתובות IP מקור מורשים להגיע אליו. כל מה שלא הותר נחסם.
- כוננים של **EBS (Elastic Block Store)** הם הדיסקים הקבועים של ה-instance. דיסקים של **instance store** הם זמניים ונמחקים כשה-instance נעצר או מסתיים.

אפשר להפעיל אחד מהקונסולה (**EC2 ← Launch instance**), או מה-CLI. זו הצורה של פקודת הפעלה; צריך להשלים AMI, key pair ו-security group אמיתיים משלנו:

```bash
aws ec2 run-instances \
  --image-id ami-0123456789abcdef0 \
  --instance-type t3.micro \
  --key-name my-key \
  --security-group-ids sg-0123456789abcdef0 \
  --count 1
aws ec2 describe-instances \
  --query "Reservations[].Instances[].{Id:InstanceId,State:State.Name,Type:InstanceType}" \
  --output table
```

ואז מתחברים עם `ssh -i my-key.pem ec2-user@<public-ip>` (שם המשתמש תלוי ב-AMI: ב-Amazon Linux זה `ec2-user`, ב-Ubuntu `ubuntu`). את פקודות Linux שתצטרכו על השרת הזה תמצאו ב[דף העזר לפקודות Linux](he/posts/linux-commands/). גם EC2 Instance Connect ו-Session Manager יכולים לפתוח shell בלי שננהל בעצמנו מפתחות SSH.

שלוש עובדות על EC2 שחוסכות כסף וכאב ראש:

- **Stop הוא לא terminate.** instance *שנעצר* לא מחויב על חישוב, אבל הכוננים שלו ב-EBS עדיין מחויבים. *Terminate* מוחק את ה-instance (וכברירת מחדל גם את כונן ה-root שלו). אם סיימנו, עושים terminate.
- **החיוב הוא לפי שנייה** (עם מינימום של דקה) ב-instances מסוג On-Demand. אפשרויות אחרות מחליפות גמישות במחיר: Savings Plans ו-Reserved Instances מחייבים אותנו לשימוש לשנה או לשלוש, ו-Spot Instances משתמשים בקיבולת פנויה בהנחה אבל אפשר לקחת אותם בחזרה.
- **כתובות IPv4 ציבוריות עולות כסף.** AWS גובה עליהן, גם על כתובת שמחוברת לשרת שלא משתמשים בו. כדאי לשאול אם ל-instance בכלל צריכה להיות כתובת ציבורית.

אם האפליקציה שלנו כבר ב-container, ייתכן שלא צריך לנהל שרתים בעצמנו: Amazon ECS ו-EKS מריצים containers במקומנו. אם זה חדש, מתחילים ב[Docker מאפס לגיבור](he/posts/docker-zero-to-hero/).

## VPC: הרשת הפרטית שלנו

כל שרת ומסד נתונים יושבים בתוך **VPC (Virtual Private Cloud)**: רשת וירטואלית מבודדת לוגית מכל השאר. בחשבון שלנו מגיע **default VPC** בכל Region, מוגדר כך שאפשר להפעיל instance ולהגיע אליו מיד. לכל דבר רציני מתכננים VPC משלנו.

- **Subnet** הוא פרוסה מטווח ה-IP של ה-VPC, והוא חי ב**אזור זמינות אחד**.
- **Route table** אומרת לאן הולכת התעבורה מ-subnet.
- **Internet gateway** מחבר את ה-VPC לאינטרנט. **Public subnet** הוא subnet שה-route table שלו שולחת תעבורת אינטרנט ל-gateway הזה. ל-**private subnet** אין נתיב כזה.
- **NAT gateway** מאפשר למשאבים ב-private subnet לשלוח בקשות החוצה (לעדכונים, למשל) בלי שאפשר להגיע אליהם מהאינטרנט. זה רכיב בתשלום, ולכן הוא שורה נפוצה בחשבונית מפתיעה.
- **Security group** היא חומת אש stateful שמחוברת למשאב, והיא זו שנשתמש בה הכי הרבה. **Network ACL** היא מסנן שני, stateless, ברמת ה-subnet.

הפריסה הקלאסית שמה את מה שפונה לאינטרנט ב-public subnets ואת כל השאר ב-private, בשני אזורים לפחות:

![VPC עם internet gateway ושני אזורי זמינות. בכל אזור יש public subnet עם שרת web ו-private subnet עם מסד נתונים. שרתי ה-web מגיעים למסדי הנתונים, ול-private subnets אין נתיב מהאינטרנט.](/images/aws-zero-to-hero/vpc-layout.svg)

הטריק המרכזי נמצא ב-security groups: מאפשרים למסד הנתונים לקבל חיבורים *רק מה-security group של שרתי ה-web*, לא מ"כל מקום". כך גם מי שמצא את הכתובת של מסד הנתונים לא יכול להגיע אליו.

## RDS: מסדי נתונים בלי לשמור עליהם

אפשר להתקין מסד נתונים על instance של EC2, אבל אז העדכונים, הגיבויים וה-failover הם העבודה שלנו. **Amazon RDS (Relational Database Service)** הוא האלטרנטיבה המנוהלת: בוחרים מנוע (PostgreSQL, MySQL, MariaDB, SQL Server, Oracle או Db2; Aurora הוא שירות קרוב שנבנה ב-AWS) ו-AWS מטפלת בהתקנה, בעדכוני תוכנה, בגיבויים אוטומטיים ובזיהוי תקלות ובהתאוששות.

- **DB instance** הוא שרת מסד נתונים מנוהל, עם **instance class** (ה-CPU והזיכרון שלו) ו**אחסון**.
- **Multi-AZ** שומר עותק המתנה (standby) באזור אחר ועובר אליו אם יש בעיה במסד הראשי. זה עניין של זמינות, לא של הרחבת קריאות.
- **Read replicas** מעתיקים את הנתונים ל-instances אחרים כדי לפזר תעבורת קריאה.
- RDS רץ בתוך ה-VPC שלנו. שמים אותו ב-**private subnets** ומאפשרים רק ל-security group של האפליקציה להתחבר.

אנחנו עדיין אחראים לסכמה, לשאילתות, לבקרת הגישה ולמה שיש בנתונים. לאפשרויות החינמיות למסדי נתונים יש כללים משלהן, אז בודקים את דף ה-free tier של RDS לפני שיוצרים אחד: מסד נתונים שנשכח רץ הוא אחת מהחשבוניות המפתיעות הקלאסיות.

## Lambda: קוד בלי שרתים

**AWS Lambda** מריצה את הקוד שלנו בתגובה לאירועים בלי שננהל שרת כלשהו. כותבים פונקציה, מחברים **trigger**, ו-Lambda מריצה אותה ומתרחבת אוטומטית לפי הביקוש. triggers טיפוסיים הם בקשת HTTP דרך API Gateway, קובץ שנוחת ב-S3, הודעה בתור או לוח זמנים.

פונקציה היא פשוט handler. זה ב-Python ומחזיר ברכה:

```python
import json

def lambda_handler(event, context):
    name = event.get("name", "world")
    return {"statusCode": 200, "body": json.dumps({"message": f"Hello, {name}!"})}
```

אירוע נכנס, תוצאה יוצאת. (זה Python רגיל, אז אפשר לנסות אותו מקומית בקריאה ל-`lambda_handler({"name": "Dana"}, None)`.)

מה כדאי לדעת:

- **תשלום לפי שימוש:** מחייבים על בקשות ועל הזמן שהקוד רץ (נמדד מול הזיכרון שהגדרנו), ושום דבר כשהיא סרק.
- **מגבלות:** הרצה אחת יכולה לרוץ עד **15 דקות**, ולכן Lambda מתאימה למשימות קצרות, לא לעבודות ארוכות.
- **חסרת מצב (stateless):** לא סומכים על כך שמשהו שורד בין הרצות. שומרים מצב ב-S3, במסד נתונים או במקום אחר.
- **Cold starts:** פונקציה שלא רצה זמן מה עלולה להתחיל לאט יותר בבקשה הראשונה.
- ה-**execution role** של הפונקציה קובע לאילו דברים ב-AWS היא יכולה לגעת. נותנים לה רק מה שהיא צריכה.

Lambda מתאימה היטב לקוד דבק ולעבודה מונחית אירועים: לשנות גודל של תמונה כשהיא נוחתת ב-S3, להריץ ניקוי לילי, לענות ל-webhook.

## מתבוננים במה שקורה

- **Amazon CloudWatch** אוסף **metrics** (CPU, מספר בקשות...), **logs** (הפלט של ה-Lambda שלנו, הלוגים של השרתים דרך agent) ומאפשר להגדיר **alarms** שמתריעים או מפעילים פעולה כשמדד עובר סף. הרבה שירותים שולחים metrics בסיסיים אוטומטית, ו-**dashboards** מציגים אותם במסך אחד.
- **AWS CloudTrail** רושם את קריאות ה-API בחשבון: מי עשה מה, מתי ומאיפה. כשמשהו משתנה בלי שציפינו, CloudTrail הוא המקום לגלות מי שינה אותו.

ה-alarm הראשון שכדאי בחשבון אישי הוא התראת התקציב מקודם. ההרגל הראשון שכדאי הוא להסתכל ב-CloudWatch Logs כשפונקציית Lambda נכשלת: השגיאה כמעט תמיד מודפסת שם.

## נמנעים מהחשבונית המפתיעה

כמעט כל סיפור אימה הוא אחד מאלה:

- **משאב שרץ ונשכח**: instance של EC2, מסד נתונים של RDS, NAT gateway או load balancer שאף אחד לא כיבה. הם מחויבים לפי שעה.
- **Access keys שדלפו** ומשמשים להרצת כורי קריפטו. לא יוצרים מפתחות ארוכי טווח, אף פעם לא עושים להם commit, ומחליפים או מוחקים את אלה שיש.
- **שאריות אחרי "מחיקה"**: כוננים של EBS, snapshots וכתובות Elastic IP שנשארים אחרי שמסיימים (terminate) שרת.
- **ה-Region הלא נכון**: משאבים ב-Region שלא מסתכלים עליו. בודקים את הבורר, או משתמשים ב-**Tag Editor** ובפירוט החיוב לפי Region כדי למצוא נשכחים.
- **העברת נתונים**: הוצאת נתונים מ-AWS או בין Regions עולה כסף.

ההרגלים שמונעים אותם: מגדירים **תקציב** ביום הראשון, **מתייגים** (tag) כל דבר שיוצרים בשם פרויקט כדי שאפשר יהיה למצוא ולמחוק אותו, **מנקים באותו יום** שמסיימים ניסוי, ומסתכלים בדף **Bills** פעם בשבוע בזמן הלמידה.

## דף העזר

| אני רוצה... | פקודה |
|---|---|
| לדעת מי אני ואיפה | `aws sts get-caller-identity` |
| להתחבר (SSO) | `aws configure sso` ואז `aws sso login --profile <name>` |
| לראות את ההגדרות הפעילות | `aws configure list` |
| לרשום את ה-buckets | `aws s3 ls` |
| להעלות / להוריד קובץ | `aws s3 cp <file> s3://<bucket>/` / `aws s3 cp s3://<bucket>/<key> ./` |
| לשקף תיקייה ל-S3 (קודם dry run) | `aws s3 sync ./dir s3://<bucket>/dir --dryrun` |
| קישור זמני לאובייקט פרטי | `aws s3 presign s3://<bucket>/<key> --expires-in 3600` |
| לרשום instances | `aws ec2 describe-instances --output table` |
| לעצור / להפעיל instance | `aws ec2 stop-instances --instance-ids <id>` / `aws ec2 start-instances --instance-ids <id>` |
| למחוק (terminate) instance ⚠️ | `aws ec2 terminate-instances --instance-ids <id>` |
| למחוק bucket ואת התוכן שלו ⚠️ | `aws s3 rb s3://<bucket> --force` |
| לציין Region לפקודה אחת | `aws <command> --region eu-central-1` |

## מילון מונחים

- **Region / אזור זמינות:** אזור גאוגרפי / קבוצת מרכזי נתונים מבודדת בתוכו.
- **IAM:** השירות ששולט בזהויות ובהרשאות.
- **משתמש root:** הזהות הראשונה והכול-יכולה של חשבון. מגינים עליה עם MFA ולא משתמשים בה ביום-יום.
- **Role:** זהות שלוקחים על עצמנו זמנית, עם credentials קצרי טווח.
- **Policy:** מסמך JSON של פעולות מותרות ואסורות.
- **S3 / bucket / אובייקט / key:** אחסון אובייקטים / המכל שלו / קובץ שמור / שם האובייקט.
- **EC2 / instance / AMI:** שרתים וירטואליים / שרת אחד / התבנית שלו.
- **EBS:** אחסון בלוקים קבוע ל-instances.
- **VPC / subnet:** הרשת הוירטואלית שלנו / פרוסה ממנה באזור זמינות אחד.
- **Security group:** חומת אש וירטואלית שמחוברת למשאב.
- **Internet gateway / NAT gateway:** מחבר VPC לאינטרנט / מאפשר למשאבים פרטיים לפנות החוצה בלבד.
- **RDS:** מסדי נתונים רלציוניים מנוהלים.
- **Lambda:** הרצת קוד באירועים בלי שרתים לנהל.
- **CloudWatch / CloudTrail:** metrics, לוגים והתראות / רישום של קריאות API.
- **Free plan / קרדיטים:** ההצעה ההתחלתית לחשבון חדש. את התנאים העדכניים קוראים באתר של AWS.
